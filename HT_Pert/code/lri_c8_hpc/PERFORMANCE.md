# C8 performance study: measured work, not projected cluster speedups

## Scope and measurement protocol

This compares the supplied `lri_phi4_C8_calculation.zip` solver against this
release, with identical frozen cutoffs, eighth order, reference states, and
`raw` or original isolated `vacuum_only` prescriptions. The original was already
using ranked bases, compiled sparse kernels and a Rayleigh-quotient method.

The clean suite contains **30 independent processes**, three per configuration.
Each process warms the relevant Numba signatures on cutoff 4, then times the
complete numerical solve: low-order calibration, basis construction, all four
reference contributions, and final eighth-order coupling assembly. Imports,
warmup, checksum/JSON serialization and checkpoint I/O are outside that timer.
Process peak RSS includes imports and warmup. No competing numerical benchmark was
run concurrently. cProfile runs are separate and excluded from the medians.

The local Linux environment has a four-CPU quota (`cpu.max=400000 100000`) and a
shared 4 GiB memory cgroup. These are **not Expanse measurements**. Per-run Python,
NumPy and Numba versions are recorded, and `BUILD_INFO.json` records the environment.
No cold-start speedup or scaling beyond four threads is claimed. Warm an appropriate
persistent cache on the compute node before measuring production kernels.

## Repeated full-solver benchmarks

Time is the median; RSS is the largest peak over the three processes. Both old and
new use the same number of threads in each comparison.

| Cutoff | Prescription | New outer backend | Threads | Old seconds | New seconds | Speedup | Old MiB | New MiB | RSS reduction |
|---:|---|---|---:|---:|---:|---:|---:|---:|---:|
| 40 | raw | stored | 1 | 7.621 | 5.115 | 1.49x | 556.8 | 392.1 | 29.6% |
| 40 | raw | stored | 4 | 3.842 | 2.032 | 1.89x | 556.8 | 392.0 | 29.6% |
| 50 | raw | stored | 4 | 18.641 | 9.323 | 2.00x | 2087.5 | 1235.3 | 40.8% |
| 50 | raw | ranked | 4 | 18.641 | 13.170 | 1.42x | 2087.5 | 1018.4 | 51.2% |
| 50 | vacuum_only | stored | 4 | 21.644 | 10.389 | 2.08x | 2117.6 | 1243.4 | 41.3% |

All individual results and coefficient differences are in `benchmarks/results/`;
`benchmarks/SUMMARY.json` is generated by `benchmarks/summarize.py`. There are no
supplied physical coefficients used as numerical targets beyond the original
low-order consistency checks.

At cutoff 40 the stored backend's one-to-four-thread numerical speedup is about
2.52x, not 4x. The ranked cutoff-50 path takes 37.712 s on one thread and 13.170 s
on four. The latter is about 41% slower than stored on four threads, while saving
another 217 MiB. Choice of backend is an explicit memory/runtime tradeoff.

## Bottlenecks identified before optimization

The original cutoff-50 raw cProfile snapshot takes 21.069 s. Its main costs are:

| Operation | Time in snapshot | Approximate fraction |
|---|---:|---:|
| Ladder `linear` calls | 10.930 s cumulative | 51.9% |
| Vertex construction's own work (excluding child ladder calls) | 3.003 s | 14.3% |
| Inner-product/quotient reductions | 3.198 s cumulative | 15.2% |
| Basis construction | 1.853 s cumulative | 8.8% |

Do not add the entire cumulative `vertices` time to the ladder time: those overlap.
The profiles and their run JSONs are retained under `benchmarks/profiles/` as
independent diagnostic runs, not as clean benchmark repetitions.

The dominant intervention is algebraic: replace large-space fourth-order
wavefunctions and Taylor jets by a cubic core trial plus its exact fourth-residual
quadratic form. High-order work moves to P<=15,Q<=12, while the P<=19,Q<=16
contribution remains in a few scalar-vector sweeps. Field-parity packing and the
creation-only outer kernel further reduce traffic. No physical support is lost.
See `docs/ALGORITHM.md` for the proof.

## Capacity test and an explicitly recorded failure

A **single** new ranked-backend raw calculation at cutoff 56, four threads,
completed in 30.244 s with 1944.9 MiB process peak RSS. It has 12,866,395 full-support
states. Its independent second-order shell residual is about -8.10e-15 and its
final tuning residual about 7.86e-10. No original C8(56) value was available for an
independent regression, and no original-versus-new speedup is assigned there.
This is a finite-cutoff capacity example, not a new physical extrapolation.

The stored-backend cutoff-56 probe was killed by the shared memory cgroup. The
OOM-kill counter increased; an unrelated service occupied about 1.39 GB. The
failed process's peak RSS was not recovered and no numerical result from it is
included. `benchmarks/CAPACITY_LIMIT.json` records this. The successful ranked run
is in `benchmarks/capacity_L56_ranked.json`. This session limit must not be
interpreted as a calibrated compute-node limit.

## Scaling that remains

Let D3,E3 denote core state/edge counts and D4,E4 the full residual space. Memory
is linear in those counts. The stored variant keeps O(E3+E4+D3*j+D4) data; ranked
removes E4 at the cost of rank/unrank work. Here j is the number of live Taylor
components. The physical state count still grows rapidly; the optimization does
not change the mathematical cutoff or make partition growth polynomial.

Representative allocation-free plans (exact dimensions; **estimated**, padded RSS):

| Cutoff | Core states | Full residual states | Stored GiB | Ranked GiB |
|---:|---:|---:|---:|---:|
| 50 | 3,096,673 | 5,248,378 | 2.40 | 2.15 |
| 60 | 11,900,137 | 22,673,328 | 6.89 | 5.53 |
| 80 | 117,687,411 | 285,718,605 | 69.1 | 49.8 |
| 100 | 796,157,247 | 2,469,662,729 | 634.8 | 362.2 |
| 118 | 3,528,133,673 | 13,607,342,826 | 3588.3 | 1984.4 |

These envelopes have not been calibrated on Expanse, are not guarantees, and must
not be substituted for measured RSS. The previous seventh-order campaign's bytes
per state are not a calibration for this new eighth-order algorithm. In particular,
a plan close to a nominal node limit does not establish that the job fits.

## Multicore and multinode boundaries

Each item is shared-memory threaded. Different cutoffs and prescriptions are
independent. A single cutoff can additionally be divided into four independent
reference contributions; tests establish equivalence of their scalar assembly.
That supplies at most four reference jobs per cutoff, not unlimited within-item
parallelism. Each node still stores complete per-item arrays, and repeats the
small calibration/basis setup. Reference splitting is not a measured four-node
speedup, does not necessarily reduce total core-hours, and does not distribute
one basis across node memories. No MPI/GPU backend is implemented.

## Reproduce

```
python benchmarks/run_suite.py      # fresh records in validation/benchmarks/
python benchmarks/summarize.py      # -> validation/summary.json
python scripts/regression_saved_grid.py --threads 4
```

For a separate profile or capacity point, use `benchmarks/bench_item.py --help`.
Capacity probes deliberately omit the production memory guard to measure the
actual workload; use the guarded `lri_c8 run` entry point for scheduled production.
